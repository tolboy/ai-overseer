# Ревью AI Overseer: Orca UI, настройки и управление ролями

Статус: статическое ревью завершено 2026-09-23; начато 2026-09-22. Исправления кода в этом артефакте предложены, но не внесены.

## Главный вывод

Overseer уже показывает роли и ход работы, собирает evidence и даёт кнопки для отдельных решений. Но целиком управлять проектом через Orca UI пока нельзя: первичная настройка, запуск, смена состава и восстановление страницы требуют CLI/YAML. Кроме этого продуктового пробела, обнаружены ошибки в обработке ответов, продолжении, показе evidence и настройках, поэтому даже существующий путь «запуск → решение → продолжение» нуждается в исправлениях.

Всего: **17 находок — 5 дефектов P1, 1 продуктовый блокер P1 и 11 находок P2**. Приоритет P1 у UI-01 означает блокер желаемого пользователем сценария без CLI, а не нарушение заявленного read-only контракта Dashboard.

## Подтверждённые находки

### UI-01 — P1, продуктовый пробел: нет единой точки управления без CLI

**Сценарий.** Пользователь открывает Overseer в Orca и хочет создать задачу, запустить цепочку, изменить состав ролей или вернуться к ожидающему решению.

**Доказательство.** `src/main/java/dev/oseer/dashboard/Dashboard.java:36-43`: сервер принимает только GET, отдаёт HTML и `/api/state`; действий управления нет. В HTML таблицы показывают данные и предлагают строку `oseer approve`, но не переход к странице решения. `src/main/java/dev/oseer/Main.java:127-142`: сама панель запускается командой `dashboard`, а `--open-orca` лишь открывает её URL.

**Последствие.** Интеграция сейчас даёт наблюдение и отдельную страницу решения уже запущенной цепочки; она не закрывает заявленный для этого ревью сценарий ежедневного управления без консольных команд.

**Рекомендация.** Добавить устойчивую точку входа из Orca: выбор проекта/задачи, запуск, настройки состава, список ожидающих решений и переход к ним. Использовать существующие сервисы проверки и принятия решений, а не строить shell-команды в браузере. Разделять конфигурацию следующего запуска и снимок параметров текущего.

### UI-02 — P1, дефект: ответы Orca gate не импортируются при открытой странице решения

**Сценарий.** Цепочка открыла DecisionPage; пользователь отвечает через Orca gate, например с телефона.

**Доказательство.** `src/main/java/dev/oseer/Main.java:1692-1708`: `lastGateRead = Long.MIN_VALUE`, затем `clock - lastGateRead >= 10_000L`. При обычном положительном Unix timestamp вычитание переполняет signed `long` и становится отрицательным. Условие не выполняется; переменная обновляется только внутри недостигаемой ветки. Чтения gate нет ни на первой, ни на следующих итерациях.

**Последствие.** Ответ в Orca не попадает в ApprovalStore, цепочка не продолжается и ждёт таймаут. Прямой POST страницы работает другим путём и не доказывает исправность мобильного gate.

**Рекомендация.** Отдельно обработать sentinel первой итерации либо использовать безопасно вычисленный `nextPollAt`; сохранить ограничение частоты. Добавить проверку именно `awaitDecision` с положительным временем и ответом через gate (существующий happy path страницы этот случай не покрывает).

### UI-03 — P2, дефект: «Дальше» закрывает решение до проверки возможности продолжить

**Сценарий.** После `baseline_failed`/`preflight_outside_scope` пользователь нажимает «Дальше», не изменив причину остановки.

**Доказательство.** `src/main/java/dev/oseer/Main.java:1669-1673` передаёт `--no-start` для всех решений страницы. Проверка `advanceWouldRepeat` перед записью включена только без этого флага (`Main.java:1257-1259`). Отказ возникает позже в `startAdvance` (`Main.java:534-540`), когда решение уже resolved; supervisor прекращает продолжение (`Main.java:1755-1757`). Страница заранее обещает продолжение (`src/main/java/dev/oseer/dashboard/DecisionPage.java:600-603`).

**Последствие.** Пользователь видит успешное действие, но следующего запуска нет. Повторно решить этот gate уже нельзя; причина отказа остаётся вне страницы.

**Рекомендация.** Выполнять проверку допустимости `advance` до `store.resolve` и независимо от технического `--no-start`. На отказе сохранять pending и выводить блокер; после успешного решения показывать фактический результат запуска и ссылку на него.

### CORE-01 — P1, дефект: зависшая запись prompt в stdin обходит все timeout

**Сценарий.** Direct CLI получает большой prompt через stdin, но завис до чтения или заполнил stdout/stderr до того, как начал читать stdin.

**Доказательство.** `src/main/java/dev/oseer/process/ProcessRunner.java:44-57`: синхронная запись всего stdin происходит до запуска drain stdout/stderr и до `waitFor(timeout)`. Этот путь вызывается из `src/main/java/dev/oseer/execution/DirectCliExecutor.java:123-136` для `prompt_delivery: stdin`.

**Последствие.** Переполнение pipe блокирует контроллер без ограничения времени; роль не завершится, human gate не появится, UI останется ждать. Настройки wall-clock/chain deadline в этот момент не действуют.

**Рекомендация.** Запускать чтение обоих потоков до записи prompt; stdin писать отдельной задачей в пределах общего deadline, на истечении закрывать streams и завершать process tree. Проверка должна включать child, который не читает stdin, и child с ранним большим stdout.

### CORE-02 — P1, дефект незакоммиченной реализации: amendment расходует бюджет вне цепочки

**Сценарий.** Цепочка дошла до `contract_gap`, исчерпав или почти исчерпав число вызовов, деньги либо время. Supervisor автоматически вызывает planner и plan reviewer.

**Доказательство.** `src/main/java/dev/oseer/Main.java:1607-1617` запускает отдельный Preparation с суффиксом `-amend`, без остатка бюджета цепочки, и не переносит `amended.roleRuns()/costUsd()/unpriced()`. `src/main/java/dev/oseer/run/Preparation.java:535-560` выдаёт собственные разрешения на дополнительные вызовы; bootstrap не реализует ограничения денег и времени исходной цепочки. Продолжение (`Main.java:549-555`) создаёт TaskLoop без этого расхода и наследует только прежнюю chain summary.

**Последствие.** Платные вызовы происходят за пределами лимита задачи; агрегаты цепочки и UI недооценивают расход. Это не утверждение об отсутствии отдельных событий в ledger: теряются связь с лимитом и итог цепочки.

**Рекомендация.** Провести amendment через общий DispatchGate исходной цепочки с reservation, остатком calls/cost/deadline и durable учётом результата, включая неуспешные попытки. Переносить расход в continuation до следующего dispatch; при исчерпанном бюджете сразу оставить решение человеку.

### CORE-03 — P2, дефект незакоммиченной реализации: неуспешный review оставляет изменённый контракт

**Сценарий.** Planner расширил контракт, а plan reviewer недоступен, завершился timeout/quota или вернул некорректный артефакт.

**Доказательство.** `src/main/java/dev/oseer/run/Preparation.java:281-282` записывает amendment в настоящий task YAML до review. Ветки отказа `Preparation.java:310-339` возвращаются без восстановления исходного текста. Откат есть только для содержательных замечаний (`Preparation.java:358-369`). При любом отказе `src/main/java/dev/oseer/Main.java:1618-1620` сообщает, что контракт остался прежним.

**Последствие.** После сообщения об отклонённой поправке следующий запуск читает уже изменённый, не прошедший review контракт.

**Рекомендация.** Проверять временный кандидат и публиковать его после успешного review с проверкой исходной версии. Как минимум обеспечить единый rollback на всех non-success/exception, не перезаписывая параллельные пользовательские правки, и сообщать фактическое состояние.

### CORE-04 — P1, дефект: land коммитит постороннее содержимое index

**Сценарий.** До `land --commit` пользователь уже staged файл под `.oseer/`, например конфигурацию или evidence. Принятые исходники не менялись.

**Доказательство.** `src/main/java/dev/oseer/run/LandCommand.java:217-227` добавляет перечисленные source paths, но затем вызывает обычный `git commit -F`, который коммитит весь index. `LandCommand.java:283-290` исключает `.oseer/` только из собственного списка. `src/main/java/dev/oseer/git/GitRepository.java:82-101` исключает эту область из source fingerprint, поэтому acceptance guard не замечает посторонний staged файл.

**Последствие.** В commit и при выбранном push попадают файлы вне показанного `result.paths`, включая локальные данные Overseer. Это нарушает обещание точного состава принятой правки.

**Рекомендация.** Перед commit проверять весь index и отказывать при лишних путях; либо создавать commit через отдельный index с проверкой дерева результата и сохранением пользовательского staging. Предпросмотр должен точно совпадать с составом commit.

### UI-04 — P2, дефект: «Отклонить» не возвращает работу исполнителю

**Сценарий.** Пользователь читает замечания и нажимает «Отклонить» с пояснением, ожидая обещанного исправления.

**Доказательство.** `src/main/java/dev/oseer/dashboard/DecisionPage.java:261-264` обещает возврат исполнителю. `src/main/java/dev/oseer/Main.java:1521,1754` исключает `reject` из продолжающих решений, поэтому supervisor завершает работу. При этом `Main.java:1284-1287` переводит карточку в RUNNING для любого решения, кроме accept/abort.

**Последствие.** Исполнитель не запускается, карточка сообщает о работе, для продолжения снова нужна команда. Сама передача заметки в явно запущенный continuation существует, но кнопка её не запускает.

**Рекомендация.** Сделать отдельное действие «Вернуть на исправление» с проверкой заметки и запуском continuation; либо честно назвать reject конечным отказом и предоставить рядом кнопку нового запуска. RUNNING выставлять только после подтверждённого старта.

### UI-05 — P2, дефект: вкладка нарратива остаётся NEEDS YOU после ответа

**Сценарий.** Цепочка запущена с `--watch`, достигла human gate, затем принято accept/abort.

**Доказательство.** `src/main/java/dev/oseer/Main.java:1284-1288` получает новый Workspace при записи ответа. `src/main/java/dev/oseer/execution/orca/OrcaWorkspace.java:81-90` создаёт новый объект, а terminal/runId сохранены только в прежнем объекте (`OrcaWorkspace.java:202-204`). `retitle` немедленно возвращается при пустых полях (`OrcaWorkspace.java:144-145`).

**Последствие.** Карточка и durable решение обновились, но видимая вкладка продолжает требовать ответа. Несколько запусков становятся трудноразличимыми по реальному состоянию.

**Рекомендация.** Хранить идентификатор вкладки вместе с lifecycle запуска; восстанавливать его при внешнем approve и завершении supervisor. Обновлять заголовок и финальную строку нарратива из authoritative состояния решения/продолжения.

### CFG-01 — P2, дефект: смена модели не всегда снимает verified

**Сценарий.** Допустимый YAML профиля содержит `verification: { verified_on: 2026-09-22, ... }`; пользователь меняет модель через `roster model` без `--keep-verified`.

**Доказательство.** `src/main/java/dev/oseer/config/RosterCommand.java:689-694` удаляет только отдельные строки с ключом `verified_on`. Inline mapping остаётся целиком. `src/main/java/dev/oseer/config/Profile.java:348-349` считает наличие ключа достаточным для verified. Такая форма YAML уже используется в `src/test/java/dev/oseer/ConfigTest.java:386,400`.

**Последствие.** Новая модель автоматически получает допуск старой проверки. Особенно прямо это проявляется у Orca/local профилей, которым не мешают проверки direct argv.

**Рекомендация.** Изменять verification структурно для всех поддержанных YAML-форм и после записи проверять `parsed.verified() == false`, если явно не задан keep-verified. UI должен показывать состояние «нужна проверка» сразу после изменения модели/effort/runner.

### CFG-02 — P2, пробел настройки: shipped Orca-профиль нельзя проверить предложенной командой

**Сценарий.** Пользователь копирует один из Orca-примеров и следует инструкции для включения Orca twin.

**Доказательство.** `examples/orca/codex-review-astra.yaml:18-23` и `examples/orca/claude-review.yaml:18-23` содержат `what_to_check`, но не `verification.probe`. `src/main/java/dev/oseer/config/RunOverride.java:219-224` советует `oseer profiles --verify <twin> --confirm`; `src/main/java/dev/oseer/config/ProfileVerifier.java:59-63` немедленно отказывает при отсутствии probe.

**Последствие.** Штатная инструкция ведёт в тупик: требуется самому написать probe или вручную подтверждать проверку. Переключение direct → Orca не является законченным сценарием настройки.

**Рекомендация.** Поставлять исполнимый ограниченный probe именно Orca-канала с launch receipt, typed artifact, settlement и проверкой read-only; дать в панели действие «Проверить профиль» с отображением результата. Не предлагать команду, которую выбранный шаблон выполнить не способен.

### CFG-03 — P2, дефект: настройка роли на неагентном этапе молча игнорируется

**Сценарий.** Пользователь передаёт `--host browser=orca` или `--use gates=<profile>` на workflow с соответствующими именами этапов, ожидая изменить исполнителя.

**Доказательство.** `src/main/java/dev/oseer/run/TaskLoop.java:1509-1525` разрешает имена всех stages, но затем пропускает любую стадию, у которой kind не ROLE. Для неё overlay не валидируется и не применяется.

**Последствие.** Опция принята без ошибки, но поведение не меняется; цепочка может начать платную работу с другой конфигурацией, чем ожидает оператор.

**Рекомендация.** До dispatch требовать ROLE для каждого ключа role/profile/effort/host overlay. В UI отображать агентные и механические этапы отдельно; недоступное действие объяснять, а для условно пропущенного этапа явно показывать «не применяется в этом запуске».

### CORE-05 — P2, дефект незакоммиченной реализации: ограничение amendment «один раз на цепочку» теряется

**Сценарий.** A вызывает amendment → B читает новый контракт и останавливается на timeout/quota → пользователь выбирает Retry/Switch → C снова находит contract_gap.

**Доказательство.** `src/main/java/dev/oseer/run/TaskLoop.java:478` блокирует повтор только по `summary.contract_amended_from`. Поле выставляется лишь при непосредственном предшественнике с причиной CONTRACT_AMENDMENT (`TaskLoop.java:4196-4198`); наследования маркера из B в C нет. Это единственные production-упоминания поля.

**Последствие.** В той же цепочке автоматически повторяется amendment, хотя политика и комментарий обещают один раз. Ошибка усиливает CORE-02, но остаётся отдельной даже после правильного подсчёта бюджета.

**Рекомендация.** Хранить durable amendment receipt на уровне цепочки и наследовать его через любой retry/switch/advance и preflight failure. Проверять наличие receipt до planner dispatch. Нужен сценарий минимум из трёх запусков.

### UI-06 — P2, дефект интеграции: один Overseer run создаёт разные Orca Runs

**Сценарий.** Запуск с `--watch` показывает стадии в Orca, затем исполняет Orca-роль или публикует human gate.

**Доказательство.** `src/main/java/dev/oseer/execution/orca/OrcaWorkspace.java:273-282` создаёт Run и хранит ID только в поле объекта. `src/main/java/dev/oseer/execution/orca/OrcaExecutor.java:259-286` использует другой ID из OrcaLifecycle и создаёт Run, если он отсутствует. `src/main/java/dev/oseer/execution/orca/OrcaDecisionGate.java:121-128` также смотрит только в lifecycle.

**Последствие.** Записи стадий нарратива и настоящий worker/gate принадлежат разным Orca Runs. Пользователь не получает единую историю задачи; дерево действий выглядит как несколько независимых работ. Конкретный внешний вид зависит от версии Orca и здесь не проверялся.

**Рекомендация.** Единый durable get-or-create Run через OrcaLifecycle для Workspace, Executor и DecisionGate. Сохранять также ID созданных stage tasks и завершать их по фактическим исходам: сейчас `OrcaWorkspace.java:261-267` результат task-create не сохраняет.

### UI-07 — P2, дефект: страница решения смешивает скриншоты разных попыток

**Сценарий.** Browser/visual QA упал, исполнитель внёс исправление, повторная визуальная проверка прошла. Пользователь принимает окончательный результат.

**Доказательство.** `src/main/java/dev/oseer/run/TaskLoop.java:4811-4813,5394-5395` сохраняет визуальные попытки в отдельные `runId--visual-qa-<attempt>`. `src/main/java/dev/oseer/dashboard/DecisionPage.java:529-539` в `runDirectories()` выбирает все каталоги `runId--*`, `harnessScenarios()` собирает все отчёты (`DecisionPage.java:449-475`), а `shots()` берёт первые восемь снимков (`DecisionPage.java:416-424`) без отбора по финальному candidate fingerprint/attempt. В секции «Что проверил браузер» также нет маркировки попытки.

**Последствие.** На финальном gate отображаются уже неактуальные состояния и проваленные сценарии. Если первая попытка дала восемь снимков, финальные могут вообще не попасть на страницу. Подписи не объясняют, к какой версии результата относится изображение.

**Рекомендация.** Показывать evidence финального кандидата по ссылкам из актуального step/coverage, а предыдущие попытки вынести в явно подписанную историю. При reuse отображать происхождение. Ограничивать галерею с возможностью открыть остальные кадры, не скрывая финальные молча.

### UI-08 — P2, продуктовый пробел: ожидающее решение переживает сервер страницы

**Сценарий.** Пользователь возвращается к вкладке позже лимита ожидания либо контроллер был перезапущен.

**Доказательство.** `src/main/java/dev/oseer/Main.java:1691,1714-1725` выходит по таймауту и закрывает DecisionPage, хотя решение остаётся pending. `src/main/java/dev/oseer/dashboard/DecisionPage.java:84,97-101` использует случайный порт/токен и останавливает HTTP-сервер в close. Восстановление предусмотрено только командой `decide` (`Main.java:1088-1115`); Dashboard не содержит действия reopen.

**Последствие.** В Orca остаётся неработающая вкладка; устойчивое решение на диске нельзя снова открыть через интерфейс Overseer без CLI. Pending и expired не объясняются на самой недоступной странице.

**Рекомендация.** Долгоживущий контроллер панели с маршрутом по run ID и восстановлением pending после рестарта. Отделить время жизни HTTP/UI от TTL решения и времени supervisor; показывать «контроллер остановлен / продолжить ожидание» с действием восстановления.

### CFG-04 — P1, дефект: writable reviewer обходит обязательную независимость вендора

**Сценарий.** При копировании профиля исполнителя в reviewer оставлен `read_only: false`. В политике reviewer всё ещё задано `require_independent_vendor: true`, а задача закономерно разрешает workspace_write для implementer. Reviewer использует того же вендора, что написал код.

**Доказательство.** `src/main/java/dev/oseer/config/Profile.java:250` допускает этот флаг без проверки семантики reviewer. `src/main/java/dev/oseer/role/RoleResolver.java:188` возвращает NONE для writable-профиля до проверки независимости на строке 191. `src/main/java/dev/oseer/role/RoleRunner.java:638` блокирует такой профиль только при отсутствии write-authority задачи. Preflight `src/main/java/dev/oseer/run/TaskLoop.java:1216-1221` использует тот же resolver; итог `TaskLoop.java:5095` считает review пройденным по ok/числу блокеров, а assurance лишь помечает как coauthor (`TaskLoop.java:3580,5099-5107`).

**Последствие.** Небольшая ошибка настройки превращает обязательное независимое review в допустимое review собственного вендора и снимает read-only-проверку executor. Наличие метки coauthor в отчёте не исполняет требование политики; DecisionPage.stages эту метку также не выводит.

**Рекомендация.** Проверять независимость по функции judging-stage/role, независимо от write flag. Для reviewer/visual_qa по умолчанию требовать read-only; если пишущий проверяющий нужен как отдельный режим, явно объявлять это в workflow и не считать его независимым review. Отказывать при несовместимой конфигурации до dispatch и объяснять ошибку в настройках.

## Рекомендации к настройкам и смене ролей

1. **Три явно разделённых уровня:** личные настройки (`~/.oseer`), проект (`.oseer/project.yaml`), параметры следующего запуска (task/overlay). Показывать источник каждого значения и действие «сбросить override». Настройки текущей работающей роли не менять задним числом; выводить её сохранённый снимок рядом с будущим составом.
2. **Состав по этапам, а не только по названиям ролей:** отдельные review/review-second, стратегия first/rotate, условия запуска, независимость, профиль, модель, effort, runner. Показывать, почему кандидат недоступен, и доступных проверенных кандидатов. Механические gates/browser не выдавать за сменяемые агентные роли.
3. **Проверка перед сохранением и запуском:** разобрать конфигурацию тем же parser/resolver, показать конкретные ошибки, эффективный состав и оценку числа вызовов. После изменения модели/канала явно снять старую verification и дать отдельное действие проверки; отметить, когда оно делает платный вызов.
4. **Настройки ограничений в интерфейсе:** calls, cost, elapsed, max fixes, failover mode, подготовка/plan-review, contract-gap route и visual QA. Показывать действие лимита на всю цепочку, включая preparation/amendment; различать строгий денежный cap и неполную оценку стоимости.
5. **Сохранение с версией и восстановлением:** preview изменений, atomic write, backup, защита от перезаписи параллельных правок. Не переносить нынешнее редактирование YAML регулярными строковыми заменами напрямую в UI.

## Узкие регрессионные сценарии для будущих исправлений

Это рекомендации к следующему этапу, не результаты выполненных тестов:

- Ответ через Orca gate при активной странице и положительном epoch времени; повторный/просроченный ответ.

- Предварительно staged `.oseer/` не попадает в accepted source commit.
- Одна цепочка использует один Orca Run; ответ обновляет watch title; pending страницу можно восстановить после остановки UI.
