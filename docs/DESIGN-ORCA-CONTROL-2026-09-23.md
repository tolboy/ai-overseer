## 1. Цель и опоры

Оператор открывает Overseer в Orca и ведёт проект целиком, не набирая команд Overseer:

1. **Удобство.** Точка входа, выбор задачи, запуск, ответы, остановка.
2. **Наблюдаемость.** Видно, кто сейчас работает, на какой модели, сколько это стоит и почему что-то не стартовало.
3. **Настраиваемость ролей.** Состав по стадиям, три уровня настроек, у каждого значения виден источник.
4. **Смена моделей.** На лету — по квотам (failover, видимый в панели). Вручную — по успеваемости вендоров, с подсказкой из корпуса прогонов.

## 3. Архитектура

### 3.1 Один контроллер — панель

`oseer dashboard` становится панелью управления: долгоживущий локальный процесс на `127.0.0.1`, открываемый во вкладке Orca (`--open-orca`).

- Браузер — тонкий клиент. Каждое действие — это POST на именованный маршрут. Маршрут вызывает тот же Java-сервис, что и соответствующая команда CLI. Shell-строк из браузера нет.
- Защиты те же, что сейчас:
  - только loopback;
  - случайный токен на процесс, вшитый в отданный HTML;
  - проверки `Host` и `Origin`;
  - ответ на решение — только через `approveDecision`;
  - `Content-Security-Policy` без внешних источников.
- Панель не хранит состояния, которого нет на диске. Всё, что она показывает, читается из `.oseer/runs/*`, `orca.json`, `decision.json`, `view-*.json`, `~/.oseer` и корпуса `~/.oseer/ledger`. После перезапуска панель восстанавливается полностью.

### 3.2 Где исполняется петля (решение оператора, вопрос В1)

- **Вариант А — в процессе панели** (так сейчас работает кнопка решения и `oseer decide`): просто, но закрытие панели убивает идущую цепочку.
- **Вариант Б — отдельный дочерний процесс на каждый запуск** (рекомендую). Панель запускает `java -cp <тот же classpath> dev.oseer.Main do|run|decide ...` отсоединённо и дальше только читает диск.
  - Перезапуск или закрытие панели не трогает работу.
  - Остановка идёт через файл-запрос (раздел 4.4), а не через убийство процесса.
  - Аренда страниц и контроллеров (`decision-page.json`, `controller_pid` в `view-*.json`) уже различает живой процесс и мёртвый.

### 3.3 Какие проекты видит панель (вопрос В2)

- **Вариант А — один проект на процесс панели** (`--project`), как сейчас.
- **Вариант Б — все Orca-worktree машины**: `orca worktree list` плюс фильтр по наличию `.oseer/`. Оператор выбирает проект в шапке. Рекомендую Б, но в поэтапной поставке (раздел 7) начинать с А.

## 4. Экраны и действия

### 4.1 Проекты и задачи — точка входа

- Список задач `.oseer/tasks/*.yaml`: у каждой последний запуск, исход, стоимость цепочки, есть ли открытое решение.
- **Новая задача**. Форма: цель (многострочная), scope (выбор из `scopes` проекта), risk, режим подготовки (`off | auto | always`).
- **Черновик контракта.** Кнопка «Составить» запускает `Preparation` (платно: планировщик и, если настроен, второй планировщик). Панель показывает скомпилированный контракт: acceptance, baseline, reproduction, бюджеты.
- **Правка критериев приёмки.** Редактор списка acceptance-команд. Сохранение идёт через `TaskSpec.parse` и не выполняет введённые команды. Отдельная кнопка «Проверить baseline» запускает только baseline-проверки (бесплатно, но локально исполняет команды проекта — об этом предупреждение).
- **Готовность.** Кнопка «Проверить готовность» — это `dry run` той же петли:
  - `would_stop`: причина остановки или «готово»;
  - состав по стадиям (`cast`);
  - план бюджета (`budget_plan`: минимум вызовов на успех, резерв на исправления);
  - доступность профилей с причинами (раздел 4.5);
  - `run_override_invalid`, `judge_not_read_only`, `independent_review_unavailable` — всё, что preflight находит до первого платного вызова.
- **Запуск** доступен, только когда готовность зелёная или оператор явно принял предупреждение. Запуск с `--watch` по умолчанию.

### 4.2 Решения

Список из фазы 2, плюс история решений по задаче. Кнопка ведёт на страницу решения — существующую или поднятую заново.

### 4.3 Активная работа

- Идущие запуски: стадия, кто исполняет (профиль, модель, effort, runner), минуты, стоимость на сейчас, число вызовов из лимита.
- Для Orca-ролей — состояние воркера из `worker-list`/`worker-show`.
- Причина, если воркер не стартовал (`OrcaExecutor.blockedOn`):
  - `folder_trust` → «Claude ждёт вопроса о доверии к папке: ответьте Yes в терминале агента, один раз на репозиторий»;
  - `cli_update_prompt` → «Codex предлагает обновиться: Skip until next version в обычной вкладке Orca».

  Рядом последний экран агента (`agent_screen_tail`).
- Контроллер остановлен → «статус неизвестен» (уже есть в Dashboard как `unknown_controller_stopped`) и действие «Проверить воркеры» (`worker-list` по записанным dispatch).

### 4.4 Остановить работу с корректным Orca settlement (новое)

Сейчас корректно остановить идущую цепочку можно только по Ctrl+C в терминале.

1. Панель пишет запрос `.oseer/runs/<id>/stop-request.json`: кто, когда, режим.
2. `TaskLoop` проверяет запрос между стадиями, `OrcaExecutor` — в цикле ожидания `check --wait` (каждое окно ≤ 60 с). `DirectCliExecutor` — по таймеру ожидания процесса.
3. Режимы (вопрос В6):
   - **«После текущей стадии»** — стадия доигрывает, дальше `stop` с причиной `stopped_by_operator`;
   - **«Сейчас»** — Orca-воркер получает `worker-stop` и `worker-release` по dispatch из `orca.json`, у direct CLI гасится дерево процессов, открытая строка стадии закрывается `failed`, карточка и вкладка получают «остановлено».
4. После остановки панель сверяет `worker-list` с записанными dispatch и показывает осиротевших воркеров, если такие остались.
5. Запуск остаётся продолжаемым (`--continue`) с сохранением оплаченных вердиктов — как после `orca_worker_not_started`.

### 4.5 Состав и настройки — три уровня

Таблица по стадиям workflow, не по ролям. Для каждой стадии:

| Поле | Источник значения |
|---|---|
| профиль-кандидаты и стратегия `first/rotate` | `~/.oseer/policy.yaml` |
| модель, effort, runner | профиль в `~/.oseer/profiles` |
| независимость (`require_independent_vendor`, `same_vendor_peer`) | policy |
| pin/effort/host на один запуск | overlay следующего запуска (task `use:` или форма запуска) |
| условие запуска стадии (`when`) и почему она пропускается | workflow + risk задачи |

- Рядом с каждым значением — источник (`личное` / `проект` / `следующий запуск`) и кнопка «сбросить override» там, где значение переопределено.
- Недоступный кандидат показан с причиной из резолвера: `profile_unverified`, `judge_not_read_only`, `vision_capability_unverified`, `same_vendor_as_writer`, `quota_exhausted_this_run`, `executable_not_found`, `role_mismatch`. Причина приходит из `RoleRunner.explainFill`, свой вывод панель не делает.
- Механические стадии (gates, browser) показаны отдельно и без кнопок смены исполнителя: после CFG-03 overlay на них всё равно отвергается.
- Текущая работающая роль показывается по снимку её запуска (`launch.requested`/`effective`) рядом с будущим составом. Задним числом она не меняется.

**Запись настроек** (вопрос В3). Сейчас `roster` правит YAML построчно регулярками, а в фазе 1 для `verified_on` пришлось отдельно поддержать flow-форму. Предлагаю общий слой `YamlEdit`:

- Операции только над известными ключами: установить скаляр, заменить flow-список, удалить ключ. Каждая работает в блочной и во flow-форме.
- Комментарии и порядок ключей сохраняются.
- Форма, которую слой не умеет править, приводит к отказу с сообщением «поправьте вручную, вот строка», а не к перезаписи.
- После записи файл снова разбирается тем же парсером (`Policy.parse`, `Profile.parse`, `TaskSpec.parse`). Если результат не тот — исходные байты восстанавливаются (сейчас так делает `rewriteAndReparse`).
- Запись атомарная (временный файл и `ATOMIC_MOVE`), с копией `*.before-panel-<время>`.
- Защита от параллельной правки: форма хранит sha256 файла на момент показа, сохранение с другим sha256 отвергается («файл изменился, перечитайте»).
- Смена модели, effort или runner снимает `verified_on` тем же путём, что `roster model` после CFG-01.

**«Проверить профиль».** Вызывает `ProfileVerifier` (для Orca-профилей — `oseer probe orca`). Перед запуском панель предупреждает, что это платный вызов вендора, и называет его. После успеха показывает транскрипт и `what_to_check`. Штамп ставится отдельной кнопкой «Подтвердить», как `--confirm`.

### 4.6 Ограничения

Форма для лимитов уровня задачи и policy. Рядом с каждым полем — его источник и действие на всю цепочку. После CORE-02 подготовка и поправка контракта считаются в той же цепочке.

| Параметр | Где | Подача в UI |
|---|---|---|
| `budgets.max_role_runs` | task | вызовы: использовано / лимит на цепочку |
| `budgets.max_cost_usd` + `cost_cap` | task | **строгий cap** (`strict`) — жёсткая граница, требует `limits.max_cost_usd` у каждого профиля; **порог** (`threshold`) — сравнение с известной ценой, вызовы без цены показаны отдельно |
| `budgets.max_elapsed_minutes`, `gate_ttl_hours` | task | время цепочки; срок жизни вопроса (не страницы) |
| `max_fix_attempts` | task | раунды исправлений |
| `failover.on_quota_exhausted` | policy | `confirm / auto / stop` с пояснением каждого |
| `--prepare`, наличие `plan_reviewer` | запуск / policy | подготовка и второй планировщик |
| `review.repair_severities` | policy | какие P-уровни идут на исправление до gate |
| `review.contract_gaps` | policy | `gate` или `plan` (пробел в контракте уходит планировщику) |
| `visual_qa.required`, `evidence` | task | браузерная и агентная проверка |

### 4.7 Смена моделей

**На лету, по квотам.** Уже работает (`failover`, `role_failover` в ledger, `quota_exhausted_this_run`). Панели остаётся только показать это:

- кто исчерпан и до какого времени, если вендор назвал окно;
- кто подменил и на какой стадии;
- ожидающая подтверждения подмена (`failover_requires_confirmation`) с кнопкой «Подтвердить» через тот же путь, что и решение.

**Вручную, по успеваемости.** Для каждой стадии панель показывает кандидатов по корпусу прогонов (`~/.oseer/ledger`, `oseer ledger --compare`):

- доля успешных чтений и записей;
- доля P1 на прогон;
- число раундов исправления, в которых стадия была причиной;
- средняя стоимость (у Orca-ролей «неизвестна» — см. 4.8);
- медианная длительность;
- размер выборки.

Ниже порога выборки (предлагаю 5 прогонов) стоит «данных мало». Предложение — это подсказка, не автоматическое переключение. Кнопка пишет pin в overlay **следующего запуска**, а не в личный roster (вопрос В5).

### 4.8 Наблюдаемость Orca-ролей

Orca-роли не пишут стоимость и токены, а Grok идёт с `model: null` (модель TUI по умолчанию). Панель показывает это явно:

- «стоимость неизвестна — Orca не сообщает»;
- «модель: по умолчанию TUI (Overseer её не задаёт)»;
- `launch.effective` помечен как квитанция запуска, а не подтверждение inference (`provider_execution_verified: false`).

В агрегатах такие вызовы идут отдельной строкой «без цены» и не считаются бесплатными.

## 5. API панели

Все `GET` — чтение. Все `POST` требуют токен формы и проверку `Origin`. Каждый маршрут — одна функция существующего сервиса.

| Маршрут | Сервис | Платно? |
|---|---|---|
| `GET /api/state` | `Dashboard.snapshot` (+ задачи, активные запуски, состав по стадиям) | нет |
| `POST /decide/<run>` | `Main.openDecision` | нет (платно продолжение после ответа) |
| `POST /task/draft` | `Preparation` | **да** |
| `POST /task/save` | `YamlEdit` + `TaskSpec.parse` | нет |
| `POST /task/ready` | `TaskLoop` dry run | нет |
| `POST /task/launch` | дочерний `oseer do/run` | **да** |
| `POST /run/<id>/stop` | `stop-request.json` | нет |
| `POST /settings/<level>` | `YamlEdit` + парсер | нет |
| `POST /profile/<name>/verify` | `ProfileVerifier` | **да** |
| `POST /profile/<name>/stamp` | `ProfileVerifier.stamp` | нет |
| `POST /run/<id>/failover/confirm` | путь `approveDecision` для решения `failover` | нет (платно продолжение) |

Каждый платный маршрут требует второго шага подтверждения. Первый POST возвращает «что будет оплачено», и только второй POST с тем же токеном выполняет действие (вопрос В4).

## 6. Что меняется на диске

- `.oseer/runs/<id>/stop-request.json` — новый: запрос остановки.
- `.oseer/runs/<id>/decision-page.json`, `orca.json.watch_terminal` — есть с фазы 2.
- `~/.oseer/policy.yaml`, `~/.oseer/profiles/*.yaml`, `.oseer/project.yaml`, `.oseer/tasks/*.yaml` — правки только через `YamlEdit`, с копией и проверкой sha256.
- Overlay следующего запуска — в задаче (`use:`) или в передаваемом дочернему процессу файле, как сейчас у Conductor (`handedOver`).

## 7. Поэтапная поставка

Каждая ступень — отдельный PR с полным набором тестов и сценариями приёмки.

1. **3a — видеть всё** (только чтение, без риска):
   - состав по стадиям с источниками и причинами недоступности;
   - лимиты с источниками;
   - failover-события;
   - наблюдаемость Orca-ролей (4.8), причины незапуска воркера.

   Приёмка: для roster оператора панель показывает ровно тех кандидатов и те причины, что `oseer roster` и dry run.
2. **3b — настройки**: `YamlEdit`, формы трёх уровней, «сбросить override», «Проверить профиль» с платным подтверждением.

   Приёмка: правка блочного и flow-YAML сохраняет комментарии; параллельная правка отвергается; повторный разбор проходит.
3. **3c — задача и запуск**: форма, черновик, правка acceptance, готовность, запуск дочерним процессом.

   Приёмка: запуск из панели и `oseer do` с теми же параметрами дают одинаковый `cast` и `budget_plan`.
4. **3d — остановка**: `stop-request.json` в `TaskLoop` и в исполнителях, режимы «после стадии» и «сейчас», сверка сирот.

   Приёмка: остановка Orca-роли оставляет `worker-list` пустым для этого запуска, а `--continue` сохраняет оплаченные вердикты.
5. **3e — подсказки по успеваемости**: агрегаты корпуса по (стадия, профиль), порог выборки, запись pin в overlay следующего запуска.
6. **3f (по желанию)** — `land` из панели: показ точного состава коммита (`paths`, `left_staged`, `already_committed`) и кнопки commit / push / PR. Каждый шаг наружу — отдельное подтверждение.

Тесты — как в фазе 2:

- `FakeOrca` для всего, что говорит с Orca;
- HTTP-тесты панели: токен, `Origin`, 403/409, двойной клик;
- тесты `YamlEdit` на блочной и flow-форме;
- ни одного платного вызова в наборе.

## 8. Что не входит

- Правка кода задачи из панели: панель управляет петлёй, а не заменяет редактор.
- Слияние (merge) из панели. `land` делает только commit, push и request — как сейчас.
- Удалённый доступ к панели не с loopback. Телефон по-прежнему отвечает через Orca gate.

## 9. Вопросы оператору

1. **В1. Где идёт петля, запущенная из панели:** в процессе панели (просто, но умирает вместе с ней) или отдельным дочерним процессом (рекомендую)?
2. **В2. Охват:** один проект на панель (как сейчас) или все Orca-worktree машины с выбором проекта (рекомендую как цель, начав с одного)?
