## Фаза 1 — границы выполнения (P1, отдельный PR от `main`)

1. **CORE-04. Коммит `land` содержит ровно принятые пути.**
   - Перед commit сверить `git diff --cached --name-only -z` с `result.paths`. При лишних путях отказывать с кодом и списком. Вариант лучше: собирать commit через временный `GIT_INDEX_FILE` и не трогать staging пользователя.
   - Предпросмотр `planned` должен совпадать с составом commit.
   - Тест: заранее застейджен файл из `.oseer/` и посторонний исходник.
2. **CFG-04. Проверяющие роли только для чтения.**
   - Для reviewer, visual_qa и plan_reviewer профиль с записью отвергается до dispatch; сообщение называет профиль и роль.
   - Независимость проверяется вне зависимости от флага записи. Метка coauthor не заменяет исполнение политики.
   - Тесты: resolver, preflight TaskLoop, `RoleRunner`.
3. **CFG-01. Смена модели или effort снимает проверку профиля.**
   - Снимать `verified_on` структурно, в блочном и во flow-YAML. После записи перечитать файл и убедиться, что `verified() == false`, если не задан `--keep-verified`.
   - Тест: inline-форма из `ConfigTest` около строк 386 и 400.
4. **S-5. Нестабильный `pilot-prepare`.**
   - Проверка «a declared deadline prepares» иногда падает с `no .oseer/project.yaml found from <bundle>/target`. Число проверок набора плавает: 7, 129, 136 за соседние прогоны на одной сборке.
   - Найти недетерминизм: порядок, время, git lock, параллельные прогоны. Сделать тест детерминированным.
   - Пока тест не стабилен, CI не может служить доказательством.

## Фаза 2 — достоверный путь через UI (P2, от `feat/decide-in-orca` или `main` после merge)

2. **UI-05. Заголовок вкладки нарратива следует решению.**

3. **UI-08. К ожидающему решению можно вернуться из Orca.**

## Фаза 3 — управление без CLI (продукт; сначала дизайн-документ и согласование)

Сначала дизайн-документ, код — только после согласования с оператором. По ревью (UI-01 и раздел «Рекомендации к настройкам и смене ролей») и опорам выше:

1. **Точка входа.** Dashboard в Orca становится панелью управления:
   - выбор проекта и задачи;
   - форма цели, scope и risk, просмотр и правка критериев приёмки, запуск с проверкой готовности;
   - список ожидающих решений;
   - остановка активной работы с корректным Orca settlement.
2. **Настройки состава.** Три уровня с видимым источником каждого значения и действием «сбросить override»:
   - личные: `~/.oseer`;
   - проектные: `.oseer/project.yaml`;
   - только для следующего запуска: task или overlay.
   Состав показывается по стадиям: профиль, модель, effort, runner, стратегия first/rotate, независимость. Для недоступного кандидата видно, почему он недоступен. Проверка перед сохранением идёт тем же parser/resolver. Действие «Проверить профиль» предупреждает, когда вызов платный. Запись атомарная, с backup и защитой от параллельных правок, а не заменами строк регуляркой.
3. **Ограничения в UI.** Calls, cost, elapsed, max fixes, failover mode, prepare/plan-review, `repair_severities`, `contract_gaps`, visual QA. Строгий денежный cap отличается от порога.
4. **Смена моделей.**
   - На лету по квотам: существующий failover, видимый на панели — кто исчерпан и на кого переключено.
   - Вручную по «успеваемости»: по корпусу прогонов (стоимость, время, доля P1, повторы по вендору и задаче) панель предлагает профиль на следующий запуск.
5. **Наблюдаемость Orca-ролей.** Сейчас они не пишут стоимость и модель; Grok идёт с `model: null` (память `orca-hosted-roles-live-20260922`). Нужно хотя бы явно показывать, что стоимость неизвестна, а для Grok — что это модель TUI по умолчанию. Сюда же видимая причина, когда worker не стартовал: `folder_trust`, `cli_update_prompt`.
